# Jotacular — screen ratings

**Version:** 1.0
**Author:** Brandon Korous
**Last Updated:** 2026-09-16

Every screen in Jotacular, scored on **Design** and **Ease** as the personas open
them. How and when to score is RULE #6 in [CLAUDE.md](CLAUDE.md); this file is
where the numbers live.

**Scored so far: 61 of 65 screens on both axes.** One more carries a Design score
with **Ease deliberately unscored** (`canvas › InkTranscript` — every reading on this
machine is canned), and **three have not been looked at at all**: `canvas › Recorder`
and `canvas › TranscriptCard` need a microphone, `canvas › ScribbleHint` needs an
iPad. Those three are the honest remainder, and RULE #4 is why they are dashes
rather than zeroes.

Update that line as rows fill in — it is the denominator, and a rating file that
does not show what it has not looked at is the same lie as an empty issue list.

**Dark mode is on** as of 2026-09-16 (ADR-116, issue 002), so `dark: unreachable`
is retired from every row. What replaced it is deliberately weaker than a score:
**every route was measured at 0 contrast failures in both themes**, which covers
the text on every pane below, but the panes were not re-composed one by one in
dark. A measurement is not a look.

**The dark pass is PAID. 49 of 52 rows say `dark: PAID`; the other three say
`dark: NOT PAID` and give the reason.** Nothing is left saying "measurement, not a
score". The ten `mcp ›` rows were never owed one — an agent surface has no theme.

**Paying it found two defects, and neither is a contrast failure** — which is the
whole argument for doing this by looking rather than by measuring:
[047](issues/047-the-colour-you-pick-is-not-the-colour-you-get-at-night.md), where
every ink swatch showed the day colour and painted the night one, and
[046](issues/046-the-add-menu-is-the-same-colour-as-the-paper-behind-it.md), where
the ⊕ menu was 1.00:1 against the paper behind it. Both are fixed and re-proved.

The three that are **not** paid, and exactly why:

| | |
| --- | --- |
| `canvas › LiveFeed` | needs two windows **both in the foreground**. This harness throttles whichever tab it is not acting on, which was proved by making each one hang in turn |
| `canvas › Photos` | needs a photo on the page, and screenshot capture failed for the rest of the session |
| `/oauth/authorize` | reached with a real registered client and **audited at 0 contrast failures in dark**, its whole structure read through the accessibility tree — but not seen. A measurement is not a look |

## The two axes

| Axis | The question |
| --- | --- |
| **Design** | Is it on-system and well-composed? Real tokens, no gradients (design.md §12), Nunito heads and DM Sans body with Caveat only as the handwritten accent, violet meaning agent, hierarchy from scale and weight, holds at 360px, and the waiting / empty / error states all present and right |
| **Ease** | Could this person do the job without help? Findable, one home per concern, the data they need already on screen, no dead ends, the words from the copy list, an obvious next step — and reachable by thumb |

Both are reported. A beautiful screen nobody can operate is not an 8; a plain
screen that gets the job done in two taps is not a 4. Where one number is wanted,
quote the lower.

**Score it at 360px first, then at desktop width.** This is a phone product; a
number taken only on a laptop is a guess about the screen people actually use.

**On dark mode.** `paper-night` exists and cannot appear — `layout.tsx` hard-sets
`data-theme="paper"` and the dark theme is scoped `:root:not([data-theme])`. Issue
002 carries it. Every row written before 002 is fixed puts
**`dark: ON since ADR-116, and its route measures 0 contrast failures in both themes — but this pane was not re-composed in dark, so that is a measurement, not a score`** in its gap column. Not "not checked" — it was
checked, and this is the answer.

| Score | Means |
| --- | --- |
| 9–10 | Nothing to fix. A 10 needs a reason written in the gap column |
| 7–8 | Right, with named nits |
| 5–6 | Works; they needed a second look or a second attempt |
| 3–4 | They got there by persistence, or it looks unfinished |
| 1–2 | They would stop, ask somebody, or leave |

**The deductions are the point.** Every scored row carries a **gap to 10** — the
specific thing that would raise it. Anything in that column which is a real defect
becomes an issue and is fixed on the spot (RULE #3), then the row is re-scored
keeping both numbers: `5 → 8`.

A screen no persona reached stays `—`. **Never infer a score** from the code, from
a sibling screen, or from the fact that it typechecks.

## How to fill a row

| Column | What goes in it |
| --- | --- |
| Screen | as printed. A title computed from the note it holds is written "depends on what is open" |
| Key | the route, or `area › Component` for a pane — what you would say to somebody to make them look at the same thing |
| Design | `1`–`10`, or `4 → 8` after a fix |
| Ease | same |
| Gap to 10 | one short phrase, plus a dark note: **`dark: PAID <date>`** once the pane has been COMPOSED in dark and looked at, or **`dark: NOT PAID`** with the reason it could not be. A contrast measurement is neither. If it is a defect, add its number |
| Persona | who opened it — `P03`. Several may score the same screen; keep the latest and note the earlier in the gap column if it differed |

## Not a screen, and so not a row

The pieces every screen shares and that are not a place you go: `Brand`, `Icon`,
`Underline`, `Reveal`, `ProseBands`, `LegalPage`, `Ink`, and the four canvas hosts that
only mount other things — `Canvas`, `CanvasStage`, `CanvasMenuHost`, `InkCanvas`,
`RemarkSurfaces`, `Remark`, `CanvasMenuItems`. Score each once in an issue if it is
wrong, and link to that issue from here, so the judgment exists somewhere findable
rather than not at all.

## Screens deliberately excluded

Redirects, downloads and machine endpoints. They have no screen and are never
scored:

`/claim` · `/share` · `/export/note/[noteId]` · `/export/space/[spaceId]` ·
`/api/*` · `/oauth/token` · `/oauth/register` · `/oauth/revoke` · `robots.txt` ·
`sitemap.xml` · `/health`

They are not listed below. **If a persona ever lands on one and sees it as a
screen, that is a `major` issue, not a rating.**

## Why the MCP tools are in this file

For every other product the agent would be plumbing. Here it is the reason the
product exists — the customer reads the agent's answer, and that answer is a
surface with a design and an ease. So the ten tools get rows.

Read the two axes differently for them: **Design** is whether the answer reads
well to the person who receives it — is it markdown a human can skim, does an
empty result say what it was empty about, is attribution clear. **Ease** is whether
the agent could pick the right tool and use it without a second attempt. Score
them from a real agent session, never from the tool definitions.

## How this list was built

    node scripts/persona-screens.mjs

It reads the code, not a nav config:

- **Pages** — every `page.tsx` under `apps/web/app`, minus the excluded list
  above. `/site/*` is served at the apex without the prefix (ADR-040), so those
  rows carry the path a person would actually see.
- **Panes, account sections and apex bands** — the component files under
  `apps/web/components`, classified by an explicit label map in the script.
- **MCP tools** — parsed out of `apps/mcp/src/tools-read.ts` and `tools-write.ts`.

**A new component with no label prints as UNCLASSIFIED and a new route prints as
UNNAMED.** That is deliberate: a screen added to the product forces somebody to
decide whether it is rateable, instead of quietly not being counted.

Regenerate it the same way after any change that adds or removes a screen, and
diff the result. A denominator that silently stops counting is worse than none.
